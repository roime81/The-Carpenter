# The Carpenter v0.7.0 — Infrastructure Digital Twin

**Release date:** 18 November 2026  
**Release type:** Feature release  
**Release commit:** `fa596dd01eb7365d251bdb2a8402030541f77032`  
**Release theme:** From deployment workflow canvas to observed infrastructure topology

## Release highlights

The Carpenter 0.7.0 introduces the first Infrastructure Digital Twin foundation. The Living Infrastructure Canvas now presents both agent execution and observed infrastructure in one organic, interconnected network. The graph is inspired by the node-mesh reference in `docs/assets/8805.jpg`.

The key change is that the graph can represent infrastructure that exists independently of a Carpenter deployment. Planned IaC remains desired state; resources become observed topology only when a worker or provider reports them.

## What's new

### Infrastructure Digital Twin

- Persistent typed resource inventory, relationship records and versioned observation history in SQLite.
- Stable resource identities derived from provider plus endpoint-scoped native identity.
- Observed physical worker hosts created and updated from worker heartbeats.
- Read-only discovery of hypervisor/runtime capabilities, private interfaces/subnets and mounted filesystems.
- Proxmox inventory for cluster nodes, QEMU/LXC guests, storage pools, virtual bridges and attached guest volumes.
- Namespace- and RBAC-scoped Kubernetes inventory for clusters, namespaces, Deployments, StatefulSets, DaemonSets, ReplicaSets, Pods, Services, service ClusterIPs, pod IPs, PVCs and visible PVs.
- Explicit topology relationships: host-to-hypervisor, host-to-VM, VM-to-bridge, VM-to-storage, namespace containment, Service-to-matching-Pod, Pod-to-ReplicaSet, ReplicaSet-to-controller, Pod-to-Node scheduling and PVC-to-PV binding.
- Provider observations from successful worker provisioning operations are imported into the same Digital Twin.

### Live Infrastructure Network

- Replaced the rigid workflow diagram with an organic light node mesh using varied node sizes and subtle blue connection strands.
- Added **All**, **Infrastructure** and **Execution** graph filters.
- Added provider-aware node sizes and category styling for compute, hypervisors, VMs, clusters, workloads, services, networks and storage.
- Added a node inspector with provider identity, native ID, actual status, selected properties, observation version and timestamps.
- Added lazy-loaded resource observation history.
- Added a **Partial** discovery state with warning counts when a provider inventory can read some objects but not every collection.

### Provider discovery and operations

- Added Proxmox and Kubernetes read-only inventory functions advertised only by workers configured for those providers.
- Added an operator/admin **Refresh topology** action with CSRF validation.
- Added authenticated Digital Twin APIs:
  - `GET /api/v1/twin/snapshot`
  - `POST /api/v1/twin/refresh`
  - `GET /api/v1/twin/resources/{resource_id}/history`
- Kept the combined graph live through the existing authenticated Server-Sent Event snapshot stream.
- Kept provider credentials on data-plane workers; resource properties are allow-listed and secret-like keys are filtered again at the persistence boundary.

## Configuration and operational notes

- Proxmox inventory requires a worker configured with its Proxmox API URL and token credentials, and the worker's configured managed Proxmox node.
- Kubernetes inventory requires a worker configured with the Kubernetes API URL and service-account token. The namespace is controlled by `CARPENTER_KUBERNETES_NAMESPACE` and defaults to `default`.
- Kubernetes inventory is limited to objects visible to that service account. Proxmox inventory is limited to the configured API token's permissions.
- Use **Refresh topology** after enrolling/configuring a provider worker or when an operator needs a new read-only inventory scan.
- A Partial result indicates one or more provider reads were unavailable or forbidden. It must not be treated as a complete inventory.
- The Digital Twin is installation-wide and shared by authenticated console users in this release. Conversation execution history remains session-scoped.
- The resource/relationship/observation store is SQLite-backed in this release; SSE snapshots are polling-backed.

## Known limitations

- AWS, Azure and GCP inventory adapters are not included in 0.7.0.
- Kubernetes discovery is namespace-scoped; full cluster-wide Node conditions/taints, Ingress/Gateway, NetworkPolicy and richer CSI/storage topology are not yet included.
- Proxmox inventory uses the cluster resource list and bounded QEMU guest configuration reads.
- Absence from an incomplete or permission-limited scan does not imply deletion. Deletion/tombstone inference is not enabled.
- Scheduled drift detection, desired-versus-observed policy evaluation and automated remediation are not included.
- The Digital Twin records observed state; it does not autonomously mutate infrastructure based on drift findings.

## Upgrade notes

This release adds three SQLite Digital Twin tables: `twin_resources`, `twin_relationships` and `twin_observations`. They are created by the application's existing store initialization/migration path. Back up the Carpenter database before upgrading any production installation.

No provider credential is moved into the control plane. Configure provider credentials on the relevant enrolled workers using the existing worker configuration and least-privilege provider permissions.

## What's next

**Infrastructure Digital Twin 2.0 is planned, not included in this release.** The staged roadmap covers:

1. Broader AWS, Azure and GCP inventory and deeper Kubernetes/Proxmox topology.
2. Scheduled reconciliation, inventory-scope evidence and safe deletion/tombstone semantics.
3. Desired-versus-observed drift detection, policy evaluation and impact analysis.
4. Human-approved remediation with execution verification, rollback/compensation and audit.
5. Scale, historical topology queries, tenant isolation and richer graph exploration.

See [Engineering Roadmap — Infrastructure Digital Twin 2.0](ROADMAP.md#6-infrastructure-digital-twin-20--planned-pipeline).
